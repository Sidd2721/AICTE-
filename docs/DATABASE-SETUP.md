# Database Architecture & Setup Guide — AICTE PS 26265

This document details the PostgreSQL configuration, role separation, Row-Level Security (RLS) enforcement, and migration workflows for the AICTE Security Deposit / FDR Portal.

---

## 1. Pinned Database Engine
- **Engine**: PostgreSQL 16 (`postgres:16`)
- **Port**: 5432
- **Database**: `app`
- **Volume Mount**: Pinned to `/var/lib/postgresql/data` (for PostgreSQL 16 compatibility)

---

## 2. Dual-Role Principle of Least Privilege

To prevent runtime application code or SQL injection from disabling RLS or tampering with DDL, database access is segregated into two distinct roles:

| Role | Permissions | Usage |
|---|---|---|
| `migrator` | `NOSUPERUSER`, `CREATEDB`, table owner | Dedicated exclusively for running Alembic schema migrations and DDL operations. |
| `app` | `NOSUPERUSER`, `NOBYPASSRLS`, DML only (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) | Runtime application connection. Cannot alter tables, create roles, or bypass RLS policies. |

### Verification Query
```sql
SELECT rolname, rolsuper, rolbypassrls, rolinherit
FROM pg_roles
WHERE rolname IN ('app', 'migrator');
```
Expected output:
- `app`: `rolsuper = false`, `rolbypassrls = false`
- `migrator`: `rolsuper = false`

## 3. Provisioning Roles and Database

Run the following SQL in a superuser psql session (e.g. `postgres` superuser):

```sql
-- 1. Create Migrator Role (Owner of schema and tables)
DO $$
BEGIN
    IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'migrator') THEN
        CREATE ROLE migrator WITH LOGIN PASSWORD 'migratorpassword' CREATEDB NOSUPERUSER NOBYPASSRLS;
    END IF;
END $$;

-- 2. Create Application Runtime Role
DO $$
BEGIN
    IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'app') THEN
        CREATE ROLE app WITH LOGIN PASSWORD 'apppassword' NOSUPERUSER NOBYPASSRLS NOCREATEDB;
    END IF;
END $$;

-- 3. Grant schema usage and privileges
GRANT CONNECT ON DATABASE app TO migrator, app;
GRANT USAGE, CREATE ON SCHEMA public TO migrator;
GRANT USAGE ON SCHEMA public TO app;

ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public
    GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app;
ALTER DEFAULT PRIVILEGES FOR ROLE migrator IN SCHEMA public
    GRANT USAGE, SELECT ON SEQUENCES TO app;
```

## 4. Row-Level Security (RLS) Context

Runtime security is governed by PostgreSQL Row-Level Security policies on all tenant tables.

Immediately after user authentication, the application must set the transaction-local RLS session variables:

```python
from app.core.rls_context import set_rls_context

set_rls_context(
    session=session,
    user_id=str(user.id),
    role="regional",           # 'institution' | 'regional' | 'bureau' | 'auditor'
    region_id=str(region.id),  # UUID string or None
    institution_id=None        # UUID string or None
)
```

This sets:
- `request.jwt.claim.sub` -> user UUID
- `request.jwt.claim.role` -> role name
- `request.jwt.claim.region_id` -> region UUID
- `request.jwt.claim.institution_id` -> institution UUID

If queries are executed without setting the RLS context, tenant table policies evaluate to `FALSE` and return zero rows.

## 5. Migration Workflow

Migrations must always be executed as the schema owner (`migrator`), not as the runtime `app` user:

```bash
cd backend
# 1. Create a revision (review autogenerated script carefully)
uv run alembic revision --autogenerate -m "describe_changes"

# 2. Apply migration to the database
uv run alembic upgrade head

# 3. Verify database matches model definitions exactly
uv run alembic check
```
